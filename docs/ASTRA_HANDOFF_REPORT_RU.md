# Отчёт для Astra: история оптимизации Handy на macOS и текущая проблема

**Дата состояния:** 22 сентября 2026  
**Репозиторий:** landco-debug/Handy_optimize  
**Целевая платформа:** MacBook Air M1, macOS Sequoia, Apple Silicon  
**База приложения:** Handy 0.9.7, Tauri 2.11.5  
**Главная цель:** минимальное потребление памяти в фоне при сохранении надёжной диктовки, горячих клавиш и обычного поведения tray-приложения.

---

## 1. Зачем нужен этот документ

Этот файл — техническая передача контекста старшей модели Astra.

За одну длинную сессию было сделано несколько последовательных архитектурных экспериментов вокруг жизненного цикла окна настроек Handy на macOS. Часть изменений давала большой выигрыш по памяти, но появлялись новые регрессии: горячие клавиши, скрытый запуск, задержки при перезапуске, а в последней экспериментальной ветке — непредсказуемые задержки и периодическое зависание внутреннего интерфейса WKWebView.

Ниже отдельно указано:

- чего хотел пользователь;
- что было исходной рабочей точкой;
- что менялось в каждой версии/ветке;
- какие проблемы реально наблюдались;
- какие гипотезы были подтверждены, а какие нет;
- какие измерения памяти получены;
- какие вопросы остаются открытыми.

Важно: этот документ не утверждает, что последняя гипотеза о причине проблемы верна. Наоборот, текущая задача — перестать добавлять точечные обходы и провести архитектурную проверку.

---

## 2. Требования пользователя, которые нельзя потерять

Пользователь хочет сохранить существующий форк, а не переписывать приложение на Swift или другой стек.

Ключевые требования:

1. Диктовка и транскрипция должны работать полностью в фоне.
2. Горячие клавиши должны работать даже если окно настроек никогда не открывалось после запуска.
3. Горячие клавиши отдельных моделей форка должны сохраниться.
4. После диктовки модель распознавания уже выгружается немедленно; это поведение менять не нужно.
5. Индикатор записи обычно отключён: **Наложение = Нет**.
6. Если индикатор отключён, его WebView не должен создаваться без необходимости.
7. Tray должен оставаться основным способом доступа к приложению.
8. Пункт **Выход** в tray должен означать настоящий выход из программы, без автоматического перезапуска.
9. При включённом **Скрыть при запуске** повторный запуск не должен неожиданно показывать окно настроек.
10. Желательно, чтобы фоновое состояние после закрытия настроек было близко по памяти к состоянию «программа запущена, но окно настроек вообще никогда не создавалось».
11. Пользователь не хочет сложной архитектуры, таймеров, polling и цепочки нестабильных workaround.
12. Пользователь — новичок и не должен вручную редактировать код или конфиги для каждой сборки.
13. Сборка делается через GitHub Actions, workflow **Build Test**, Apple Silicon.
14. Локально на Mac инструменты разработчика специально не устанавливаются.

## 3. Важная особенность окружения

Все тестовые сборки используют один и тот же bundle/app identifier:

**com.pais.handy**

Поэтому разные сборки и даже старые версии делят одну и ту же папку Application Support и один и тот же persistent settings store.

Типичная директория:

**~/Library/Application Support/com.pais.handy/**

Настройки лежат в:

**settings_store.json**

Это уже однажды привело к ложному впечатлению, что старые версии внезапно тоже сломались.

В настройках сохранилось:

**keyboard_implementation = tauri**

После этого даже старые сборки начали использовать Tauri Global Shortcut вместо Handy Keys.

Следствие:

- сочетания только из модификаторов перестали назначаться;
- появлялась ошибка:
  **Tauri shortcuts must include a main key (letter, number, F-key, etc.) in addition to modifiers**;
- пользователь подумал, что проблема распространилась на все версии.

После возврата backend на **Handy Keys** версия 5.1 снова нормально работала.

Поэтому Astra должна обязательно учитывать: часть поведения зависит не только от бинарника, но и от общего persistent state.

## 4. Исходная стабильная контрольная версия V4

Контрольная ветка:

**backup-v4-before-v5-memory**

HEAD:

**b2a110bae1267244c297b55e5d88634e2cd6236a**

Эта версия считается последней исходной стабильной точкой до экспериментов с памятью.

Её характерное поведение:

- окно настроек создаётся обычным способом;
- на macOS закрытие окна перехватывается;
- вместо уничтожения окна выполняется **prevent_close + hide**;
- поэтому WKWebView остаётся жить;
- приложение и горячие клавиши работают стабильно;
- цена стабильности — интерфейс настроек продолжает занимать память после закрытия.

Именно V4 нужно использовать как baseline для регрессий.

Для форка был отдельно исправлен GitHub Actions workflow:

**.github/workflows/build-test.yml**

Он предназначен для ручной сборки Apple Silicon без Apple Developer signing.

Путь запуска:

**Actions → Build Test → Run workflow → нужная ветка**

Это важно, потому что другие workflow давали красные статусы, не связанные непосредственно с компиляцией кода:

Это существовало до части экспериментов с памятью и не являлось доказательством ошибки компиляции.

Автоматическая macOS-сборка могла падать на шаге импорта Apple Developer Certificate.

В форке нет необходимых signing secrets.

Поэтому для реальной проверки использовался именно ручной **Build Test**.

# 6. История экспериментов

## 6.1 V5 — уничтожаемое окно настроек

Исторический commit:

**81010e06b490512c2a37bd43900d4e4ed5e57e10**  
Сообщение: **Apply v5 memory lifecycle optimization**

Идея V5:

- убрать зависимость фоновой диктовки от React/App.tsx;
- перенести необходимую инициализацию shortcuts/input в Rust;
- вместо hide при закрытии реально уничтожать settings WebView;
- при повторном открытии создавать окно заново;
- оставить основной Rust/Tauri процесс живым после уничтожения последнего окна;
- не создавать recording overlay при старте, если он отключён.

### Что удалось

При закрытых настройках основной процесс Handy действительно оставался жив.

В одном из тестов после закрытия окна оставались:

- Handy ≈ 42 МБ;
- Handy Graphics and Media ≈ 17 МБ;
- Handy Networking ≈ 6 МБ.

При более удачном цикле Graphics and Media также исчезал.

Сам Web Content процесс типа **tauri://localhost** исчезал после уничтожения settings window.

Это показало, что освобождение существенной части WebView памяти возможно.

### Проблемы

Первая V5 показала:

- диктовка не реагировала;
- горячие клавиши не назначались;
- ошибка:
  **Failed to send register command**.

Первичная гипотеза была, что HandyKeys manager thread инициализировался слишком рано.

Позже выяснилось, что одновременно влиял и persistent setting **keyboard_implementation = tauri**.

То есть ранняя диагностика смешивала две причины:
1. реальные изменения lifecycle/init;
2. сохранённый backend горячих клавиш.

## 6.3 Регрессия Start Hidden

После V5.1 обнаружилось:

при включённой галочке **Скрыть при запуске** окно настроек всё равно появлялось.

Причина была найдена в логике инициализации:

- Enigo/Input был перенесён на более поздний этап;
- ранняя проверка видела, что Enigo ещё отсутствует;
- это ошибочно интерпретировалось как проблема Accessibility;
- приложение принудительно показывало окно настроек.

---

## 6.4 V5.2 — исправление Start Hidden

Исторический commit:

**6d4a38761040a14b4d09fa6256b5933d56e93e7f**  
Сообщение: **Respect start-hidden after deferred macOS input init**

V5.2 убирала ложное раннее решение «показать окно, потому что Enigo ещё не готов».

Цель:

- уважать Start Hidden;
- принудительно показывать настройки только при реальной ошибке permission/input уже после запуска фоновой части.

### Почему эту линию всё равно решили не продолжать

После перекрёстной проверки документации Tauri/WebKit было решено, что destroy/recreate settings WebView плюс удерживание приложения после закрытия последнего окна — более рискованный lifecycle.

Ключевой вывод:

- WebKit на macOS сам использует process pool;
- число Network/GPU/WebContent процессов не обязано быть детерминированным;
- destroy/recreate добавляет больше lifecycle edge cases;
- Tauri не предоставляет особенно простой и «первоклассный» режим tray-only app без окон после уничтожения последнего окна;
- V5 уже породила несколько регрессий.

Был выбран более консервативный подход.

# 7. Возврат к V4 и идея Lazy Settings Window

## 7.1 Ветка v4-lazy-settings-window

Ветка:

**v4-lazy-settings-window**

Текущий HEAD:

**be5d6d3ed854b7dfe4689a694eef1db1b4c6c27d**

Также на этот commit сейчас указывает **main**.

Основные commits:

- d5f58bf281c81dc5ba72eb8c391989b0465e9f00 — Add lazy macOS settings window to v4
- be5d6d3ed854b7dfe4689a694eef1db1b4c6c27d — Keep disabled recording overlay lazy on macOS

### Архитектурная идея

Не уничтожать окно после каждого закрытия.

Вместо этого:

- если Handy запускается скрыто — settings WebView вообще не создавать;
- background shortcuts/input должны жить независимо от окна;
- когда пользователь впервые открывает настройки — создать окно;
- после этого закрытие снова делать старым надёжным V4-способом: hide.

Это компромисс:

- обычный ежедневный hidden startup получает минимальную память;
- после первого открытия settings память интерфейса остаётся до следующего полного restart;
- зато нет постоянного destroy/recreate WebView.

### Измерения

С настройками открытыми:

- tauri://localhost: 90.7 МБ
- Handy: 58.9 МБ
- Graphics and Media: 24.7 МБ
- Networking: 6.0 МБ

Итого:

**≈180.3 МБ**

При запуске Handy, когда окно настроек вообще не открывалось, но диктовка активно использовалась:

- только Handy ≈ 52.0 МБ

Это очень важное измерение.

Оно показывает, что на данном Mac фон без создания WebView действительно может быть примерно в диапазоне 50 МБ.

Позже в одном экспериментальном restart-цикле фон показывал даже около 28.2 МБ у процесса Handy, но этот результат нельзя считать устойчивым baseline.

# 9. v4-close-restarts-background — текущая экспериментальная линия

Ветка:

**v4-close-restarts-background**

Текущий HEAD на момент этого отчёта:

**f1ddbe086f00ef168646fef2c2f524d5509cc8c7**

Последовательность commits:

- 056e63869c583156a44e097d9e7e5b541bdbb975 — Restart to clean background when settings close
- 964f77956307dd3865e8395e912ceb320067d6fd — Run deferred background restart on Idle
- 19ecd2872866431ea7b2fb9878eee52837431516 — Remove redundant restart footer button
- 30bbfa95cd361bfc75ec918688432f6ed9fac4a9 — Remove obsolete restart frontend binding
- db4b20a59b4fe68d7ab883fd337b1985298f8898 — Make close-to-background restart immediate on macOS
- f1ddbe086f00ef168646fef2c2f524d5509cc8c7 — Release single-instance socket before fast restart

### Целевая семантика

На macOS:

**Красный крестик settings window:**

- окно сразу скрывается;
- если Handy в tray state Idle — полный restart в background;
- если Recording или Transcribing — restart откладывается;
- при первом переходе tray обратно в Idle выполняется restart;
- если пользователь успел снова открыть настройки до deferred restart — pending restart отменяется.

**Tray → Выход:**

- настоящий app.exit(0);
- никаких restart.

### Почему отслеживался только Recording/Transcribing

Уже существующий tray state содержит:

- Idle
- Recording
- Transcribing

Есть штатная функция:

**tray::is_idle(app)**

Решено не создавать отдельную state machine для model download/model loading.

Это было сделано специально, чтобы не усложнять архитектуру.

# 10. Первая проблема restart: задержки 20–30 секунд

Изначально использовался Tauri:

**request_restart()**

Пользователь сообщил:

- первые циклы иногда быстрые;
- затем закрытие крестиком начинало ждать 20–30 секунд.

Было найдено, что request_restart использует graceful runtime exit path.

В коде Handy при shutdown присутствуют фоновые компоненты и lifecycle teardown.

В частности у TranscriptionManager есть idle watcher, который проверяет состояние блоками по 10 секунд, а Drop содержит join фонового watcher thread.

Однако важно не переоценивать этот факт: сам по себе этот watcher не был окончательно доказан как единственная причина задержки.

После чтения Tauri был выбран другой API:

**app.restart()**

Идея:

- выполнять restart на main thread;
- перед этим принудительно сохранять settings store;
- не ждать полного RunEvent::Exit lifecycle.

# 11. Вторая проблема restart: single-instance race

После перехода на быстрый app.restart появилась гипотеза о гонке с:

**tauri-plugin-single-instance 2.3.2**

Handy использует single-instance plugin.

На macOS новый процесс может встретить socket предыдущего экземпляра.

Так как быстрый restart не проходит обычный RunEvent::Exit, появилась опасность, что singleton socket не будет своевременно освобождён.

В commit:

**f1ddbe086f00ef168646fef2c2f524d5509cc8c7**

перед app.restart было добавлено:

**tauri_plugin_single_instance::destroy(app)**

Цель:

- явно освободить singleton socket;
- только затем spawning replacement process.

# 12. ТЕКУЩАЯ КРИТИЧЕСКАЯ ПРОБЛЕМА

После сборки с single-instance destroy пользователь провёл повторные циклы.

Фактическое наблюдение:

1. Первые примерно 5–6 циклов:
   - закрытие крестиком;
   - restart почти моментальный.

2. Затем:
   - один restart занял около 5–7 секунд.

3. Следующие циклы:
   - задержки выросли до 10–20 секунд.

4. Появился второй, более тревожный симптом:
   - settings window иногда открывается;
   - стандартные кнопки macOS titlebar работают:
     - закрыть;
     - свернуть;
     - развернуть;
   - но внутренний UI Handy полностью перестаёт принимать клики;
   - проблема проявляется спонтанно, примерно «один цикл работает, другой нет».

Это уже не выглядит как простая задержка single-instance socket.

Особенно важен симптом:

**NSWindow chrome жив, но содержимое WKWebView не реагирует на input.**

Это может указывать на проблему жизненного цикла WebKit/Wry/Tauri либо на гонку процесса/событий после серии быстрых перезапусков.

На данный момент корневая причина НЕ установлена.

Не следует продолжать добавлять случайные sleep/delay/workaround без более фундаментальной проверки.

# 14. Что подтверждено, а что было только гипотезой

## Подтверждено наблюдением

- Baseline V4 работает устойчиво, но hide сохраняет WebView память.
- Запуск без создания settings WebView существенно снижает footprint.
- При hidden/lazy запуске диктовка может работать без settings window.
- Overlay был отключён во всех основных memory тестах.
- В одном clean background тесте Handy занимал около 52 МБ.
- При открытом settings UI суммарный footprint мог быть около 180 МБ.
- V5.1 при правильном backend Handy Keys работала с горячими клавишами.
- Persistent settings shared между версиями реально влияют на поведение.
- Tauri backend не принимает shortcut из одних модификаторов.
- В текущей close-restart ветке повторные restart циклы деградируют по времени.
- В текущей close-restart ветке WKWebView content иногда перестаёт реагировать на клики, при том что native window chrome остаётся жив.

## Вероятно, но не доказано окончательно

- Ранняя инициализация HandyKeys в первой V5 могла создавать race.
- request_restart graceful lifecycle мог участвовать в длинных задержках.
- single-instance socket мог участвовать в fast-restart race.
- repeated rapid process restart может взаимодействовать с macOS LaunchServices/WebKit/Tauri event lifecycle.
- задержки могут быть связаны не с одним механизмом, а с несколькими teardown/startup subsystems.

## Не следует считать доказанным

- Что idle watcher с 10-секундным sleep был единственной причиной задержек.
- Что single-instance socket был полной причиной деградации.
- Что переменное число WebKit helper processes является утечкой.
- Что любые 1–2 отдельных memory snapshots показывают устойчивый долгосрочный выигрыш.

# 15. Почему переменное число WebKit процессов само по себе не показатель

В macOS WKWebView/WebKit использует несколько типов процессов:

- Web Content;
- Networking;
- Graphics/Media;
- shared process pool.

Поэтому количество процессов может меняться между циклами.

Для оценки памяти важнее:

1. суммарная память всей группы Handy;
2. есть ли живой Web Content процесса settings UI;
3. воспроизводимость после одинаковой последовательности действий;
4. растёт ли footprint от цикла к циклу;
5. сохраняется ли интерактивность WebView.

Нельзя считать «два процесса вместо трёх» доказательством успешной оптимизации.

# 18. Вопросы к Astra

Просьба не начинать сразу с правок. Сначала дать архитектурный диагноз.

## Главный вопрос

Почему многократный цикл:

**open settings → close by macOS red X → immediate full app restart in background → open settings again**

сначала работает быстро, а после нескольких повторов начинает:

- задерживать restart на 5–20 секунд;
- иногда создавать окно, в котором native titlebar работает, а WKWebView content перестаёт принимать mouse clicks?

### Что особенно нужно проверить

1. Безопасно ли вообще использовать Tauri AppHandle.restart многократно подряд на macOS desktop app с:
   - WKWebView;
   - tray;
   - tauri-plugin-single-instance;
   - global shortcuts;
   - nspanel plugin;
   - Store plugin;
   - autostart/SMAppService;
   - WebKit process pool.

2. Есть ли у Tauri/Wry/WebKit известные lifecycle ограничения при быстром restart одного и того же bundle.

3. Может ли новый process запускаться раньше, чем:
   - старый NSApplication полностью отпустил resources;
   - WebKit networking/content process pool завершил IPC;
   - Carbon/global hotkey registrations снялись;
   - accessibility event taps/HandyKeys thread teardown завершились;
   - tray/menu bar objects уничтожены.

4. Может ли это объяснить «window chrome responsive, web content not clickable».

5. Надёжнее ли вместо in-app restart использовать другой архитектурный путь, например:
   - отдельный лёгкий Rust/background core, а settings process отдельный;
   - companion/helper process;
   - один постоянно живущий native host без WebView и отдельный settings WebView процесс;
   - обычный hide плюс редкий explicit restart;
   - lazy settings only без автоматического restart;
   - другой штатный macOS lifecycle.

6. Не является ли самый разумный финальный вариант просто:
   - V4 + Lazy Settings Window;
   - никаких автоматических restart;
   - пользователь получает ~50 МБ, пока настройки не открывались;
   - после открытия UI память выше до следующего естественного quit/relaunch;
   - зато максимальная стабильность.

7. Можно ли освобождать только WKWebView content safely без уничтожения или restart всего Tauri process.

8. Если restart всё-таки оставлять, какой официальный/надежный macOS/Tauri механизм нужен, чтобы он был детерминированным и не вызывал деградацию после серии циклов.

# 21. Предпочтение пользователя на текущем этапе

Пользователь больше не хочет бесконечной серии мелких lifecycle patches.

- зависающий UI;

# 22. Краткий итог

Самая важная уже доказанная вещь:

**Lazy startup действительно даёт большой memory win без обязательного создания settings WebView.**

Самая важная текущая проблема:

**автоматический restart при каждом закрытии окна пока не доказал стабильность и после серии циклов показывает деградацию и WebView input freeze.**

Поэтому Astra стоит сначала решить вопрос архитектуры, а не продолжать лечить симптомы.
