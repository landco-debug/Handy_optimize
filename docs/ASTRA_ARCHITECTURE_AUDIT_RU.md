Это новый процесс, а не повторная инициализация `NSApplication` внутри прежнего PID. Но **ожидания завершения старого процесса перед запуском нового здесь нет**. Нет и ожидания окончания работы WebKit helpers или готовности shortcuts нового экземпляра.

Простая внутрипроцессная утечка сама по себе не объясняет рост задержки через новые PID.

**В отложенном restart найдены конкретные гонки.**

В [`restart_in_background_if_pending()`](https://github.com/landco-debug/Handy_optimize/blob/f1ddbe086f00ef168646fef2c2f524d5509cc8c7/src-tauri/src/lib.rs) флаг снимается через `swap(false)`, после чего перезапуск ставится в очередь main thread.

До выполнения этой очереди пользователь может снова открыть настройки или начать запись. Но closure уже безусловно вызывает restart: повторной проверки отмены и занятости нет. Поэтому обещание комментария «повторное открытие отменяет pending restart» выполняется **только до постановки restart в очередь**.

Есть и обратная гонка: между `is_idle()` и установкой `RESTART_WHEN_IDLE = true` worker может успеть опубликовать Idle. Тогда событие пройдёт раньше установки флага, и restart останется ждать следующего Idle.

Наконец, **Idle в tray — не доказательство готовности приложения к завершению**. Оно не охватывает все загрузки моделей, фоновые задания и незавершённые команды изменения настроек. Atomic-флаг обеспечивает атомарность самого флага, но не согласованность этих операций.

Эти дефекты подтверждены кодом. Они достаточны, чтобы отвергнуть текущую схему для стабильного выпуска, хотя сами по себе не объясняют все наблюдаемые задержки при циклах без диктовки.

| **NSApplication** | Tauri запускает новый binary напрямую, без ожидания полного завершения предыдущего экземпляра | Это не управляемая последовательность «старый завершён → новый готов» |
| **SMAppService** | Handy проверяет статус login item и пропускает ненужную регистрацию | Доказательств, что autostart создаёт повторные экземпляры при каждом крестике, нет |

Источники реализации: [single-instance 2.4.0](https://github.com/tauri-apps/plugins-workspace/blob/single-instance-v2.4.0/plugins/single-instance/src/platform_impl/macos.rs), [Store 2.4.2](https://github.com/tauri-apps/plugins-workspace/blob/store-v2.4.2/plugins/store/src/store.rs), [global-shortcut 2.3.2](https://github.com/tauri-apps/plugins-workspace/blob/global-shortcut-v2.3.2/plugins/global-shortcut/src/lib.rs), [nspanel используемого commit](https://github.com/ahkohd/tauri-nspanel/blob/da9c9a8d4eb7f0524a2508988df1a7d9585b4904/src/lib.rs). Проверена также macOS-реализация single-instance 2.3.2: значимая здесь логика сокета та же.

Для `com.pais.handy` версии делят не только settings, но и путь single-instance socket: `/tmp/com_pais_handy_si.sock`. Поэтому параллельные запуски разных сборок могут вмешиваться в эксперимент ещё до загрузки UI.

Apple описывает `SMAppService.mainApp` как механизм запуска при входе пользователя. Это не протокол restart и не подтверждение автоматического восстановления после каждого выхода. ([developer.apple.com](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp?utm_source=chatgpt.com))

**Гипотезу о 10-секундном watcher следует существенно понизить.**

В [`TranscriptionManager`](https://github.com/landco-debug/Handy_optimize/blob/44bab108c240c3d779b56e7e389951a7fca4d306/src-tauri/src/managers/transcription.rs) действительно есть `sleep(10s)` и `join()` в `Drop`. Но:

- быстрый main-thread restart не гарантирует вызов этого `Drop`;
- даже graceful Tauri restart нельзя приравнивать к уничтожению всего Rust managed state;
- `Drop` имеет ранний выход при `Arc::strong_count(&engine) > 1`;
- watcher сам удерживает clone менеджера.

Таким образом, цепочка «restart всегда ждёт watcher, поэтому тормозит по 10 секунд» **кодом не подтверждается**. Более того, владение менеджером со стороны watcher заслуживает отдельной проверки корректности остановки. Это существующий технический долг, а не доказанная причина регрессии.

**Безопасен ли вообще repeated restart по официальной реализации?**

Корректный ответ состоит из двух частей:

- **Restart — поддерживаемая возможность Tauri.** Нет основания утверждать, что macOS запрещает многократный перезапуск tray-приложения или что шестой запуск нарушает установленный лимит.
- **Гарантии стабильности именно вашей комбинации и частоты перезапусков нет.** Доступность API не означает, что он останавливает произвольные workers приложения, ждёт освобождения всех внешних ресурсов и подтверждает готовность нового экземпляра.

Tauri прямо документирует пропуск exit events при вызове `restart()` на главном потоке и предлагает `request_restart()` для надёжной доставки этих событий. Но доставка событий сама по себе не создаёт недостающий протокол остановки Handy. ([docs.rs](https://docs.rs/tauri/latest/tauri/struct.AppHandle.html?utm_source=chatgpt.com))

Также нельзя объяснять проблему «единым вечным WKProcessPool, который накапливается между PID». Проверенные источники этого не устанавливают. Apple отдельно отмечает, что создание нескольких `WKProcessPool` больше не даёт прежнего эффекта управления процессами; проектировать освобождение памяти вокруг ручного переключения pools не стоит. ([developer.apple.com](https://developer.apple.com/documentation/webkit/wkprocesspool?utm_source=chatgpt.com))

**Сравнение архитектур с вашими приоритетами.**

| Вариант | Преимущества | Риски и цена | Решение |
|---|---|---|---|
| **A. V4, окно всегда существует, close = hide** | Минимум переходов lifecycle; известная рабочая база | Память WebView расходуется даже без открытия настроек | Хороший контрольный вариант |
| **B. Lazy startup, затем close = hide** | Экономный фон до первого открытия; последующие открытия без повторной инициализации приложения | UI остаётся в памяти после открытия; нужно проверить фоновую инициализацию ввода | **Рекомендуется** |
| **C. Full restart при каждом close** | Может вернуть footprint к состоянию без UI | Прерывание фоновой работы, гонки, повторная инициализация, уже наблюдаемая деградация | **Не оставлять в рабочей версии** |
| **D. Destroy/recreate settings** | Core и shortcuts остаются живы; возможно освобождение части памяти UI | Асинхронное уничтожение, повторная загрузка frontend, очистка подписок, отсутствие гарантии полного освобождения helpers | Возможный будущий эксперимент |
| **E. Отдельный core/helper и UI process** | Завершение UI отделено от диктовки | IPC, владение settings, permissions, упаковка, обновления и восстановление соединения | Сейчас неоправданно сложно |

По варианту D предыдущий отчёт слишком категоричен. **Tauri поддерживает уничтожение и создание окон**, а runtime предусматривает `ExitRequested` при уничтожении последнего окна, которое приложение может предотвратить. Это не запрещённый lifecycle.

Подтверждение — [`WebviewWindow::destroy()`](https://github.com/tauri-apps/tauri/blob/tauri-v2.11.5/crates/tauri/src/webview/webview_window.rs) и обработка уничтожения последнего окна в runtime. В [Wry 0.55.1](https://github.com/tauri-apps/wry/blob/wry-v0.55.1/src/wkwebview/mod.rs) есть путь удаления WebView и IPC handler.

Но `destroy()` отправляет событие runtime: успешный возврат вызова ещё не означает завершённое уничтожение. Нужны согласованные состояния создания/уничтожения, освобождение frontend-подписок и правильное различение закрытия последнего окна и явного Quit. **Поддерживаемость API не доказывает надёжность уже испытанной V5.**

Для вашего форка B выигрывает именно тем, что не требует решать эти задачи ради памяти редко открываемых настроек. Наблюдавшиеся ≈52 МБ относятся к конкретному тесту hidden startup, а не к гарантированному постоянному бюджету. После открытия UI следует принять более высокий расход; разница между приведёнными снимками могла превышать сто мегабайт, не только «несколько десятков».

**Степень уверенности в выводах.**

- **Подтверждено кодом:** fast restart пропускает exit hooks; новый процесс запускается до выхода старого; `destroy(single-instance)` удаляет только путь; deferred restart имеет гонки; tray Idle не является общим барьером завершения работы.
- **Подтверждено вашими наблюдениями, без моего воспроизведения:** задержки растут, иногда не работает web-content, hidden startup даёт существенно меньший footprint.
- **Сильная архитектурная гипотеза:** нестабильность связана с повторением несогласованного полного lifecycle; разделение native/web объясняет возможность живого titlebar при неисправном содержимом.
- **Не доказаны:** конкретная утечка WebKit, накопление event taps после смерти процессов, throttling LaunchServices, единственная виновность watcher, single-instance или SMAppService.

**Минимальный план после принятия рекомендации.**

Если рабочей основой становится нынешний `main`, **для перехода на B архитектурные правки вообще не нужны**: он уже реализован. Не следует переносить туда экспериментальную close-restart логику.

Если нужно преобразовать именно экспериментальную ветку, минимальный функциональный diff ограничивается двумя файлами:

| Файл | Изменение |
|---|---|
| [`src-tauri/src/lib.rs`](https://github.com/landco-debug/Handy_optimize/blob/f1ddbe086f00ef168646fef2c2f524d5509cc8c7/src-tauri/src/lib.rs) | Удалить restart-флаг, маркер, `StartHiddenOnce`, функции подготовки/выполнения restart и вызов из `CloseRequested`; сохранить lazy creation и `prevent_close + hide` |

Отдельная небольшая задача надёжности, обнаруженная аудитом: в `commands/mod.rs` функция `initialize_shortcuts()` маркирует инициализацию успешной после вызова функции без результата; в `shortcut/handy_keys.rs` ошибки регистрации логируются, но итог может оставаться `Ok(())`. Поэтому `background_input_ready` **не является строгим подтверждением работоспособности shortcuts**.

Исправлять это следует отдельным компактным изменением в:

- `src-tauri/src/commands/mod.rs`;
- `src-tauri/src/shortcut/mod.rs`;
- `src-tauri/src/shortcut/handy_keys.rs`.

Цель — достоверный результат инициализации и регистрации, без повторной регистрации при обычном открытии настроек. Это не основание возвращать destroy/restart. Обновление Tauri/Wry, переписывание autostart, Store, frontend и watcher в минимальный переход на B не входят.

**План проверки — минимум 20 последовательных циклов на состояние.**

Перед каждой серией: одна активная сборка, зафиксированные SHA и версия macOS, одинаковая модель и исходный settings snapshot; `handy_keys`, `overlay_style = none`, немедленная выгрузка модели, hidden startup и включённый tray. Backend проверять также после серии: настройки общие для сборок.

| Серия | Последовательность |
|---|---|
| **A: 20 циклов** | Открыть настройки → проверить клики/ввод → закрыть → проверить фоновую диктовку |
| **B: 20 циклов** | Сначала hidden startup и несколько диктовок без открытия UI; затем 20 циклов открытия/скрытия без выхода из приложения |
| **C: 20 циклов, только диагностически** | Открыть → проверить UI → закрыть → проследить старый и новый PID → подтвердить готовность диктовки → повторить |

В серии B циклы 1–10 провести в Idle, 11–15 — с закрытием во время записи/транскрипции, 16–20 — с быстрым повторным открытием. В каждом цикле проверять General/History/Models, один обратимый toggle, поле ввода и hotkeys моделей.

Записывать отдельно:

- время открытия до **реальной интерактивности**;
- PID приложения;
- успешность диктовки и вставки;
- память приложения и относящихся к нему helpers;
- для C — моменты исчезновения старого PID, появления нового, готовности shortcuts и UI.

При задержке или некликабельном UI сначала сохранить логи и снять образцы процессов через Activity Monitor, затем продолжать. Это не требует Xcode или Developer Tools.

Для B критерии приёмки: **20/20 интерактивных открытий, неизменный PID, отсутствие прерванных диктовок и потерянных hotkeys, отсутствие нарастающих многосекундных задержек**. Память после первого открытия может остаться выше исходной; проверять нужно её последующую тенденцию, а не возврат к 52 МБ. После серии — настоящий Quit через tray и новый hidden launch.

**Выбор для выпуска: нынешний `main`, вариант B.** Он сохраняет уже полученный выигрыш скрытого старта и убирает необходимость многократно перезапускать исправно работающую фоновую диктовку ради закрытия окна настроек.
